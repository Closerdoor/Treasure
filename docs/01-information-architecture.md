# 个人收藏馆设计文档 01：信息架构与路由规则

## 1. 项目定位

本项目是一个"精选型个人收藏馆"，不是全量资料库。

核心特征：

- 只收录经过馆长筛选的作品
- 以馆长筛选后的作品集合为核心，作品资料以公开社区信息和标准元数据为主
- 展示站点静态优先，部署到 GitHub Pages
- 内容录入、搜索补全、标准化整理在本地完成
- 后续支持多用户标签、用户评分、评论等增强能力

## 2. 总体架构

项目分为两层：

1. 展示站点
   - 面向访客
   - 采用 Astro 静态生成
   - 部署到 GitHub Pages
   - 正式内容来源于仓库内的结构化内容文件

2. 本地内容工坊
   - 面向馆长
   - 负责录入、搜索、补全、确认、整理、产出正式内容
   - 支持手动输入与 YAML 批量导入
   - 使用本地数据库保存草稿、候选结果、采集缓存和待确认数据

## 3. 一级模块与子模块

当前第一版固定为以下模块结构。

### 3.1 影视

- 短片

### 3.2 书

### 3.3 音乐

- 专辑
- 单曲

- 演唱会现场
- 音乐人专题

### 3.4 游戏

- 单机游戏
- 独立游戏

说明：

- 模块级模板独立设计，不强行共用同一套字段和版式
- 全站视觉系统、导航、标签逻辑、搜索体验保持统一
- 子模块优先复用所属一级模块的模板骨架，再按子模块做字段和区块差异化

## 5. 用户场景

### 5.1 访客场景

- 从首页进入，浏览策展内容和最近新增
- 进入具体模块，按子模块查看作品
- 使用标签、年份、地区等筛选内容
- 查看作品资料、馆长评分、少量馆长备注和延伸信息
- 通过 Giscus 参与评论

### 5.2 馆长场景

- 直接输入：`新增电影：xxx`
- 或在 YAML 配置文件中批量添加待录入内容
- 由本地工坊执行搜索和候选匹配
- 若出现重名或歧义，先人工确认目标条目
- 自动补全基础元数据
- 馆长补充少量人工字段、标签与评分
- 生成正式内容文件与站点页面数据

## 6. 内容录入模式

支持两种录入方式：

1. 单条口头录入
   - 例如：`新增电影：星际穿越`
   - 例如：`新增电影：星际穿越 2014 导演诺兰`

2. 配置文件批量录入
   - 使用 YAML 文件维护待录入内容清单
   - 适合一次性新增多条内容

录入规则：

- 如果输入信息不足，允许先进行多来源搜索
- 如果搜索到多个可能目标，必须先让馆长确认
- 基础元数据允许自动补全
- 标签、馆长评分和少量人工字段由馆长确认或录入

## 7. 正式内容与本地数据库

### 7.1 正式内容存储

正式内容文件采用：

- `Markdown + Frontmatter`
- 构建时生成索引 JSON

原因：

- 馆长备注、补充说明和少量长文本适合使用 Markdown 管理
- Frontmatter 适合保存结构化字段
- 构建生成 JSON 便于列表页、搜索页、标签页使用

### 7.2 本地数据库

本地工作数据库采用 `SQLite`。

用途包括：

- 录入草稿
- 搜索候选缓存
- 外部来源映射
- 图片下载记录
- 待确认状态
- 自动补全结果缓存

说明：

- SQLite 只用于本地工作流
- GitHub Pages 不依赖数据库运行
- 最终对外发布的数据全部固化进仓库

## 8. ID 与 URL 规则

### 8.1 设计原则

详情页 URL 不再使用 `slug-年份`，改为使用稳定数字 ID。

原因：

- 同一年可能存在同名作品
- 跨模块也可能同名，例如书、电影、音乐作品重名
- 数字 ID 更适合长期维护、重命名和外部映射

### 8.2 ID 结构

采用固定长度数字 ID：

`MMSSNNNNNN`

字段含义：

- `MM`：一级模块编号
- `SS`：子模块编号
- `NNNNNN`：该子模块下的递增内容编号

示例：

- `0101000001`
- `0101000002`
- `0302000015`

### 8.3 一级模块编号

- `01`：影视
- `02`：书
- `03`：音乐
- `04`：游戏

### 8.4 子模块编号

#### 影视

- `01`：电影
- `02`：电视剧
- `03`：动漫
- `04`：纪录片
- `05`：短片

#### 书

- `01`：网络小说
- `02`：经典文学
- `03`：名著
- `04`：散文随笔
- `05`：漫画

#### 音乐

- `01`：专辑
- `02`：单曲
- `03`：原声带
- `04`：演唱会现场
- `05`：音乐人专题

#### 游戏

- `01`：单机游戏
- `02`：独立游戏
- `03`：网游
- `04`：手游
- `05`：主机游戏

### 8.5 编号规则

- `NNNNNN` 在各子模块内独立递增
- 同一条内容一旦生成 ID，不再变更
- 即使标题修改、标签修改或补充字段，ID 也保持稳定
- 删除内容后，已使用的编号不回收

### 8.6 URL 结构

详情页 URL 采用固定格式：

`/{module}/{submodule}/{id}`

示例：

- `/video/movie/01010001`
- `/video/tv/01020003`
- `/book/classic/02020008`
- `/music/single/03020015`

说明：

- `module` 与 `submodule` 使用英文固定枚举值
- URL 中不强依赖标题字段
- 页面展示标题由内容数据决定
- 如有需要，可在页面中单独展示英文名或拼音别名，但不作为正式主路由的一部分

## 9. 图片策略

图片资源统一存入项目仓库。

当前已确认规则：

- 海报、封面、剧照等图片均进入仓库
- 当前阶段优先保证资料完整性，不强制压缩

需要在后续技术方案中补充的维护规则：

- 图片目录规范
- 命名规范
- 同一条内容的图片数量上限
- 后续是否增加自动压缩流程

## 10. 互动功能边界

### 10.1 V1 已启用

- 馆长评分
- Giscus 评论

### 10.2 V1 预留

- 用户评分
- 综合评分
- 多用户标签
- 用户身份体系

说明：

- 第一版页面只展示馆长评分
- 用户评分的数据结构和展示位置先预留，不在第一阶段落地

## 11. 设计约束总结

当前需要在后续所有设计和实现中保持一致的约束如下：

- 站点采用 Astro 静态生成并部署到 GitHub Pages
- 仓库公开，评论系统采用 Giscus
- 内容录入支持口头单条输入和 YAML 批量导入
- 存在歧义时，必须先确认候选内容再入库
- 正式内容文件使用 Markdown + Frontmatter
- 构建时生成 JSON 索引
- 本地数据库采用 SQLite
- 图片统一存入仓库
- URL 使用模块/子模块/数字 ID 的固定结构
- 模块模板独立设计，视觉系统统一
