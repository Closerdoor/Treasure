# 个人收藏馆设计文档 03：数据模型与内容链路

## 1. 设计目标

本设计文档用于统一以下问题：

- 结构化数据从哪里来
- 前台页面消费哪一份数据
- 审阅用 Markdown 与正式前台数据之间是什么关系
- 本地采集、整理、确认、归档的链路是什么
- 前台需要哪些字段，哪些只是工作流数据

## 2. 当前数据分层结论

当前项目中的单条内容，以“内容目录单元”的形式存在。

以电影为例：

```text
content/video/movie/0101000003/
  data.json
  0101000003.md 或 index.md
  source.json
  raw/
  images/
```

各文件职责：

- `data.json`
  - 当前前台站点的正式结构化数据来源
  - 详情页展示的数据以它为准
- `md` 文件
  - 用于人工审阅、快速浏览、对照和后续归档
  - 不作为前台页面直接展示来源
- `source.json`
  - 用于字段溯源和来源记录
- `raw/`
  - 存放采集过程中的原始页面或原始数据
- `images/`
  - 存放该条内容关联的图片资源

## 3. 前台展示边界

当前已明确以下硬约束：

- 前台站点不是博客或笔记站点
- 前台不直接渲染 `md` 文档
- 前台页面展示应基于 `data.json` 等结构化数据组织
- `md` 文件只服务于馆长工作流，不进入公开展示主链路

## 4. 当前内容生产链路

新增一条内容时，整体链路可理解为：

```text
输入线索
  -> 搜索候选
  -> 人工确认目标
  -> 聚合多方数据
  -> 生成 / 更新 data.json
  -> 生成审阅用 md
  -> 整理图片与来源材料
  -> 前台消费结构化数据
```

说明：

- `data.json` 是给站点看的正式数据
- `md` 是给馆长看的审阅与归档材料
- 两者一一对应，但职责不同

## 5. 录入入口

支持两种入口：

### 5.1 单条录入

适用场景：

- 临时新增一条内容
- 先输入标题，再让系统搜索
- 补充少量线索以便定位目标

示例：

```text
新增电影：星际穿越
新增电影：星际穿越 2014 导演诺兰
```

### 5.2 YAML 批量录入

适用场景：

- 一次性录入多条内容
- 批量导入待整理清单

建议目录：

- `ingest/batches/*.yaml`

## 6. 状态流转

每条内容在进入稳定状态前，建议经过以下状态：

- `draft`
- `searching`
- `pending_confirm`
- `enriching`
- `pending_review`
- `ready`
- `published`
- `archived`

说明：

- `pending_review` 表示结构化数据已形成，等待人工审阅
- 审阅过程中可参考对应的 `md` 文件
- 发布并不意味着生成博客文章，而是意味着可进入前台公开站点

## 7. 数据来源策略

自动补全采用多来源聚合与交叉核对。

当前重点来源：

- 豆瓣
- IMDb
- TMDB
- 烂番茄
- 维基百科 / 百度百科等补充来源

原则：

- 优先使用结构化程度高、稳定性强的数据源
- 中文与国际来源交叉比对
- 出现关键字段冲突时进入人工确认

## 8. 当前前台核心字段

前台电影详情页当前主要消费以下类型的字段：

### 8.1 基础信息

- `id`
- `module`
- `submodule`
- `title`
- `originalTitle`
- `year`
- `genre`
- `country`
- `runtime`
- `releaseDate`
- `director`
- `writer`
- `cast`

### 8.2 评分与来源

- 豆瓣评分
- IMDb 评分
- TMDB 评分
- 烂番茄评分
- 基于四方数据计算出的综合平均分

说明：

- V1 的主评分是综合平均值
- 当前不再将 `curatorRating` 视为前台主评分字段

### 8.3 内容分区数据

- `synopsis`
- `story`
- `reviews`
- `videos`
- `images`
- `soundtrack`
- `links`
- `source` / `source.json` 中的可公开来源信息
- `series`（后续补充）
- `similar`

## 9. 当前详情页分区映射

电影详情页当前按以下分区消费结构化数据：

1. 详情介绍
   - 主要来自 `story`

补充说明：

- `synopsis` 用于列表页、首页卡片和详情页顶部的短简介
- `story` 用于详情页 `详情介绍` Tab 的完整剧情
- `reviews` 应为精选长评或高质量评语，不再使用短评凑数

`story` 的补充约束：

- 已上映作品：应整理为可独立阅读的完整剧情，而不是对 `synopsis` 的轻微扩写。
- 未上映或未公开完整剧情的作品：只能写公开剧情梗概、公开人物关系和已公开阶段性故事，不得补写未公开后续。
- 这类条目的 `story.note` 必须明确标注“基于公开剧情物料整理，非完整剧情/非完整人生全程”。

2. 演职员
   - 主要来自 `director`、`writer`、`cast`、其它职员信息

3. 精彩影评
   - 主要来自 `reviews`

4. 视频
   - 主要来自 `videos`

5. 图片（剧照 / 海报）
   - 主要来自 `images`

6. 音乐
   - 主要来自 `soundtrack`

7. 外部来源
   - 主要来自 `links` 与来源说明

右侧栏：

- 系列作品
- 相似作品

## 10. 当前列表页数据需求

影视模块列表页当前需要的数据包括：

- 标题
- 原名
- 海报
- 年份
- 子模块
- 类型
- 地区
- 导演
- 综合评分
- 简短摘要或概览信息
- 标签

说明：

- 首页模块预览卡片应尽量与列表页卡片保持一致
- 列表页默认按上映时间排序
- 当前排序不作为用户可切换项开放

## 11. 图片组织

当前图片与单条内容一起放在对应目录中管理，后续站点可在构建阶段决定是直接引用还是复制到公开资源目录。

图片类型可包括：

- 主海报
- 补充海报
- 剧照
- 人物头像
- 视频封面图

命名原则：

- 基于内容 ID 目录归类
- 文件名不依赖标题
- 保持来源可追踪

## 12. 本地数据库职责

SQLite 仍然只用于本地工坊，不作为线上数据库。

当前职责包括：

- 导入任务记录
- 待确认条目记录
- 候选匹配缓存
- 来源数据缓存
- 图片与资源记录
- ID 分配记录

## 13. ID 与路由

ID 仍采用：

```text
MMSSNNNNNN
```

URL 仍采用：

```text
/{module}/{submodule}/{id}
```

说明：

- `id` 作为稳定主标识
- 标题变化不影响路由
- 前台页面展示标题由结构化数据决定

## 14. 当前 V1 与旧方案的差异

以下内容已经从旧方案中更新：

- 不再以 `Markdown + Frontmatter` 作为当前前台主内容来源
- 不再默认把馆长评分作为 V1 主评分
- 不再默认把馆长短评、馆长长评作为前台核心字段
- 当前前台以外部平台资料聚合与结构化展示为主

## 15. 当前结论

当前阶段已经明确：

- `data.json` 是前台正式数据来源
- `md` 是人工审阅与归档材料，不进前台主链路
- V1 前台评分以四方平台综合平均值为主
- 详情页采用“基础信息 + Tab 分区 + 右侧关联栏”的结构
- 列表页承担搜索、筛选、分页与进入详情页职责
- 当前优先完成影视模块闭环
