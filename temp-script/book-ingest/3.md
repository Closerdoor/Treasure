处理网文站点的反爬，尤其是起点这类将“字体混淆”（Font Obfuscation）玩得炉火纯青的平台，确实是一个非常经典的攻防博弈。

在构建高度结构化的 Bento-box 网格布局和具有呼吸感的排版时，底层数据的干净程度是致命的。任何一个字段（比如字数、推荐票数、连载状态）如果因为反爬而抓到一堆乱码 `&#x...`，都会直接破坏整个界面的视觉和谐。

针对这种特殊的字体混淆，在 Python 生态下通常有以下四种维度的解法，从“正面硬刚”到“降维打击”都有：

### 思路一：正面硬刚 —— 动态字体文件解析（Font Parsing）

这是最硬核但也最根本的方法。网文平台的逻辑通常是：每次刷新页面，都会动态生成一个新的 `.woff` 或 `.ttf` 字体文件，并将页面上的数字或特定汉字替换为这些字体文件中的 Unicode 私有区字符（PUA）。

* **核心工具：** `fontTools` 库（Python）
* **攻防拆解：**
1. **抓包拦截：** 在请求网页 HTML 的同时，提取 CSS 中 `@font-face` 指向的动态字体文件 URL 并下载。
2. **解析字形：** 使用 `fontTools.ttLib.TTFont` 将字体文件转换为 XML 结构。你会发现这些动态字体其实包含了数字（0-9）或常用字的“绘制路径（坐标点）”。
3. **建立映射库：** 因为每次请求的 Unicode 编码都在变，但**字体的绘制形状（Glyph）通常是不变的**（或者只有微小形变）。你需要预先提取一组基准字体，计算其字形的特征值（比如坐标序列的 hash，或者简单的结构比对），从而建立 `当前乱码字符 -> 真实数字/文字` 的动态映射字典。
4. **文本替换：** 用映射好的字典去替换 HTML 里的乱码。



### 思路二：降维打击 —— 视觉识别渲染层（OCR）

既然平台在前端耍花招欺骗代码，那我们就直接模拟人类的眼睛。这种方法特别适合抓取频率不高，但要求准确率的场景（比如资料馆的按需录入）。

* **核心工具：** `Playwright` / `Selenium` + `PaddleOCR`
* **攻防拆解：**
1. **所见即所得：** 使用无头浏览器加载目标页面，等待字体文件完全渲染。
2. **精准截图：** 定位到被混淆的 DOM 节点（比如 `.count-text`），让 Playwright 仅对该元素进行局部截图。
3. **图像转文本：** 将截图送入轻量级的本地 OCR 引擎（如百度开源的 PaddleOCR）。对于数字和高清晰度渲染的汉字，现在的 OCR 准确率几乎是 100%。


* **优势：** 完全无视对方底层的加密逻辑更新，只要页面还让人看，就能抓到。

### 思路三：绕道而行 —— 降级抓取或寻找 API（App Sniffing）

Web 端的反爬往往是最严的，因为浏览器环境最开放。但很多平台的移动端 App 或是某些特定的小程序，其数据接口往往是干净的 JSON。

* **核心工具：** `mitmproxy` / `Charles` / `Appium`
* **攻防拆解：**
1. 用抓包工具代理手机网络，打开目标网文 App。
2. 寻找书籍详情页的 API 请求。很多时候，App 端为了性能和本地渲染的稳定性，直接下发的是未混淆的明文数据。
3. 拿到 API 签名（Sign）规则后，直接在 Python 中模拟移动端请求。



### 思路四：借力打力 —— 提取前端解密 JS 逻辑

有些站点的混淆并不是通过动态字体，而是通过前端加载一段混淆过的 JS 代码，在本地执行解密后再渲染到 DOM 树上。

* **核心工具：** `PyExecJS` / 浏览器调试工具的 AST 还原
* **攻防拆解：** 找到负责解密的 `.js` 文件，将其扣取出来，使用 Python 执行该 JS 环境，传入密文直接获取明文。但这需要一定的 JavaScript 逆向工程能力。

---

如果为了保证你资料馆开发初期的数据流转顺畅，我建议先从 **思路二（Playwright 截图 + OCR）** 跑通 MVP（最小可行性产品），因为它实现最快且最不容易因为对方策略微调而报错。等后期需要大批量更新数据时，再投入精力研究 **思路一（fontTools 映射）**。
